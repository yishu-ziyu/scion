# 023 — Living Reader 长程研究决策验收

## 目的

本任务是持节当前北极星 `product/021` 的高难度端到端验收，不是 Living Reader 的预设产品结论。

持节必须独立回答：**The Living Reader 下一阶段最值得开发的 3 个能力是什么？为什么？**

通过标准不是“写出一份看起来完整的报告”，而是完成一次可恢复、可追溯、可验证的真实产品决策。

## 固定任务

### 第一阶段：理解项目

1. 定位并读取 GitHub 仓库 `yishu-ziyu/living-reader`。
2. 记录仓库 URL、默认分支、验收时 HEAD、读取时间与文件结构。
3. 阅读 README、产品与设计文档、主要入口、核心数据结构、测试、Issue、最近提交，以及能够证明当前状态的内容。
4. 读取当前 Chrome 中已经打开的 Living Reader 网页、PDF、比赛要求、设计稿或文档。
5. 产出当前产品能力地图，严格区分：已实现、正在实现、只有构想、产品约束、技术约束。
6. README 或文档中的愿景不得单独作为“已实现”证据；已实现能力必须有代码、测试或可观察运行证据。

### 第二阶段：用户研究

1. 建立至少 **80 条有效用户讨论记录**。
2. 来源尽量覆盖 Reddit、Hacker News、知乎、小红书、X、GitHub Issues / Discussions、Product Hunt、YouTube 评论区，以及阅读器、PDF、AI 学习产品社区。
3. 不以搜索摘要计数；必须打开实际内容并获得足以支持观察的正文或评论。
4. 一条有效记录必须包含稳定来源、用户问题或使用情境、原始内容依据、观察与采集时间。
5. 同一讨论的转贴、镜像、重复评论只计一次。无法读取正文、只有营销文案或没有实际用户信息的不计数。
6. 沿新出现的概念继续扩散搜索，不把关键词限制为“AI PDF”。
7. 重点覆盖：复杂阅读阻塞、放弃 AI PDF 的原因、离开原文搜索的时机、需要图/模拟/时间线/地图/关系图的时机、留下理解与重新找到理解的方式、PDF 聊天产品的重复抱怨。

### 第三阶段：竞品与邻近产品

1. 建立至少 **30 个产品记录**。
2. 覆盖 AI 阅读器、浏览器、NotebookLM 类研究工具、交互式教材、数据可视化、知识图谱、模拟器、学习工具、游戏化知识产品与 Generative UI。
3. 每个产品必须实际打开官方页面、产品界面、文档或演示；搜索摘要不计数。
4. 每个产品记录必须回答：解决的问题、核心交互、独特能力、可迁移内容、看起来很酷但价值不足的内容。
5. 对进入最终候选依据的重要产品，继续读取至少一个独立用户评论或讨论。

### 第四阶段：交叉验证

把用户需求、竞品能力、Living Reader 当前实现与 Owner 产品理念放进同一个分析框架。

任何进入最终前三的能力，至少需要：

- 2 条相互独立的用户证据；
- 1 条竞品或邻近产品证据；
- 1 条 Living Reader 当前架构或代码依据。

证据不足必须标记为“假设”。相互矛盾的证据必须并列保留，不能只保留支持结论的材料。

### 第五阶段：决策与飞书交付

最终只允许留下 **3 个**下一阶段能力。每个能力必须回答：用户需要时刻、行为改变、现在做的原因、其他功能后置原因、当前代码距离、最小可验证版本与成功指标。

在飞书创建一张结构化研究表和一份最终决策文档。决策文档第一屏只回答：下一步做什么、为什么、什么暂时不做；证据放在后面。

## 证据空间

### 证据记录

每条记录至少包含：

| 字段 | 要求 |
|---|---|
| `record_type` | 用户讨论 / 产品 / 仓库 / 当前浏览器上下文 / 产品理念 |
| `source` | 可重新打开的 URL 或仓库对象标识 |
| `source_title` | 来源标题 |
| `captured_at` | 采集时间 |
| `user_problem` | 用户问题或使用情境；不适用时说明 |
| `raw_basis` | 支持观察的原始内容片段或结构化摘录 |
| `observation` | 直接观察到什么 |
| `inference` | 从观察推断什么；不得与观察混写 |
| `confidence` | 高 / 中 / 低，并说明原因 |
| `related_product` | 相关产品；不适用时为空 |
| `living_reader_capability` | 对应 Living Reader 能力候选 |
| `priority` | 高 / 中 / 低 |
| `stance` | 支持 / 反对 / 混合 / 中性 |
| `dedupe_key` | 规范化 URL + 讨论或内容对象标识 |

### 计数规则

- 80 条用户讨论与 30 个产品是两个独立计数器。
- 只有形成合格证据记录后才增加计数。
- 同一作者在同一讨论中重复表达同一问题只计一条。
- 搜索结果摘要、无法打开的链接、纯营销介绍与模型自行概括不计数。
- 任务恢复后必须复用 `dedupe_key`，不能因重放而重复计数。

## 验收门

| Gate | 通过条件 |
|---|---|
| G23-1 项目理解 | 能力地图覆盖五种状态；每个“已实现”判断有代码、测试或运行证据；记录仓库 HEAD |
| G23-2 用户证据 | 至少 80 条合格且去重后的用户讨论记录；失败来源不计数 |
| G23-3 产品证据 | 至少 30 个实际打开研究的产品记录；重要候选含独立用户证据 |
| G23-4 交叉验证 | 最终每个能力满足 2 用户 + 1 产品 + 1 代码依据；反证并列；不足项标记假设 |
| G23-5 产品决策 | 最终恰好 3 个能力，逐项回答七个决策问题，并明确暂不做项 |
| G23-6 飞书交付 | 研究表和决策文档均创建成功；字段、计数、链接和第一屏内容经重新读取验证 |
| G23-7 长程可靠性 | 中断后可恢复；不重复计数；单一网页失败不会终止；只因验证码、付款、授权或不可逆操作等待用户 |
| G23-8 无虚假完成 | 任一计数、证据门或飞书回读未通过时不得标记完成 |
| G23-9 可视进度 | 侧栏持续显示五阶段、真实 80/30 计数、当前动作目的、运行健康、下一步与交付物；暂停时无陈旧运行状态；操作数不冒充任务进度 |

## 正式验收输出

正式运行必须留下任务快照、用户可见进度快照、阶段状态、去重后的证据空间导出、失败来源与替代路径、三个能力的证据覆盖矩阵、飞书研究表 URL、飞书决策文档 URL、飞书回读结果与最终任务回执。

## 模型与系统边界

- 正式模型默认 MiniMax-M3；配置其他兼容模型时，仍使用同一验收门。
- 模型负责理解、搜索策略、分析与表达。
- 持节系统负责计划、检查点、证据记录、去重、计数、恢复、外部写入与完成验证。
- 模型声明 `done` 不改变任何计数，也不能绕过 G23-1 至 G23-8。

## 任务中断边界

登录墙、页面变化、来源失效、搜索质量差与信息冲突属于自主处理范围。只有验证码、付款、授权或不可逆操作可以进入 `waiting_user`。
