# 第 3 章：并行化（Parallelization）

## 书里的机制
- 工作流里有些子任务不依赖彼此的即时输出，应同时跑，而不是等上一步做完再开始下一步。（「并发执行多个组件，包括LLM调用、工具使用乃至整个子智能体」；「独立任务同时运行」）
- 典型形状是：先同时搜多个来源，再同时总结各来源，最后顺序合成一份答案。（「*同时*搜索来源 A 和来源 B」；「此步骤通常为顺序执行，需等待并行步骤完成」）
- 对外部 I/O（API、数据库、网页加载）特别有效：总时间不再等于各步相加。（「在处理具有延迟的外部服务（如API或数据库）时尤其有效」；「总处理时间等于所有单个任务持续时间之和」）
- 实现上要先识别「无直接顺序依赖」的节点，再在一个汇聚点等齐再往下走。（「识别工作流中不依赖其他部分输出的环节并将它们并行执行」；「其结果可在图中的后续汇聚点进行聚合」）
- LangChain 的写法是 `RunnableParallel`：同一输入同时跑摘要链、问题链、术语链，再管道进综合提示词。（「RunnableParallel 是并行运行多个可运行对象的关键构造」；`full_parallel_chain = map_chain | synthesis_prompt`）
- Google ADK 的写法是 `ParallelAgent` 同时跑多个研究员 `LlmAgent`，再交给 `SequentialAgent` 里的 `MergerAgent` 综合。（「一旦所有研究员完成并将结果存储在状态中，它就完成」；「首先执行 ParallelAgent 进行研究，待其完成后执行 MergerAgent」）
- 书也写了成本：并发会加重设计、调试和日志。（「采用并发或并行架构会引入显著复杂性和成本，影响设计、调试和系统日志」）
- 其它用例（书里当同一机制的实例，不是另一套架构）：多 API、分块分析、多段内容同时起草、多项独立校验、多模态同时看、A/B 多变体再选优。（「同时查询航班价格、酒店可用性」；「同时为文章生成三个不同标题」）

## 结论
- 部分做成
- 完成度：58
- 一句话：`TaskManager.prepareIndependentInstructionTabs` 会在 `driver.run` 前调用 `BrowserContext.openIndependentTabs`（先两次 `chrome.tabs.create`，再 `Promise.all` 等加载 / `_attachAllowedPage`），但 `runObserveActLoop` 每步仍只一次 `decide`，仓库没有 `RunnableParallel` / `ParallelAgent`。

## 对持节业务的意义
持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。

```mermaid
sequenceDiagram
  participant User as 侧栏用户那一句
  participant TM as TaskManager.runCurrentRound
  participant Tabs as openIndependentTabs
  participant Loop as runObserveActLoop
  participant Model as llm.invoke
  User->>TM: 两个独立 https URL
  TM->>Tabs: prepareIndependentInstructionTabs
  Tabs-->>TM: 两页 URL+标题写入 targetRefs / open_tab
  TM->>Loop: driver.run
  Loop->>Model: Verified pages 两行 + 当前页
  Model-->>User: 写出两个标题；侧栏两张 task-page-card
```

这一章改的是交「打开 A 和 B，写出标题」那一次：以前模型先 `go_to_url` A、再观察、再开 B，中间多付一次整页加载和一次决定。
现在代码在第一次 `decide` 前就把两个后台标签 `chrome.tabs.create` 出去，侧栏长出两张页卡片，模型应写标题而不是再开第二个站。
失败场景：用户写了「先 A 再 B」却被并行打开，顺序证据对不上 `checkOrderedSourceVisitProof`；或其中一页 404，用户只看见一张卡片，模型仍可能编第二个标题。
搜索板上「打开前 3 条」要等当前页已经是 SERP 才会在 `observe` 里扇出；刚交「搜索再打开前 3 条」时，启动阶段 `prepareIndependentInstructionTabs` 不会开结果页。
两个用户任务同时跑不是本章机制：`TaskManager.dispatch` 对第二件 `start` 返回 `invalid_transition`，侧栏仍一次只做一件事。

## 完成方案
- Goal: 在现有 `createLlmControlDriver` + `TaskManager` 上，把「独立工作同时跑、齐了再综合」收口到搜索板多条打开，并让第一次 `decide` 稳定看见已打开各页的 URL 和标题；不引入第二套 agent、不并行打三只模型。
- Hard bar: when I 交「打开 https://www.iana.org 和 https://en.wikipedia.org/wiki/Web_browser，写出两个页面的标题」, I see 第一次 `llm.invoke` 的 HumanMessage 含两行 `Verified pages:`，侧栏 `task-work-stream` 出现两张 `task-page-card`，且两次 `chrome.tabs.create` 都在任一次 load 完成前、`followForeground === false` 时 `active: false`。when I 交「先打开 https://one.test/a 再打开 https://two.test/b」, I see `openIndependentTabs` 不被调用。when I 在 `https://www.google.com/search?q=browsers` 交「打开前 3 条结果并写出标题」, I see 同一次 `observe` 里最多 3 个结果标签被 create，随后第一次 `decide` 的 `Verified pages:` 含这 3 个 URL。
- 改哪些现有文件（不要新开第二套 agent 树）
  - `chrome-extension/src/background/agent/backends/control-llm.ts`：给 SERP `openAndDescribeIndependentPages` 补与 `manager.test.ts` 同级的观察后记录断言；打开完成后、本次 `decide` 前必须能读到新页。
  - `chrome-extension/src/background/task/verified-step-records.ts` `formatVerifiedPagesForPrompt`：若 `independentTabRecords` 或观察写入了 `quote`，把摘句一并列入 `Verified pages:`，不要另写 `independentPagesMemory` 第二条通道。
  - `chrome-extension/src/background/task/independent-urls.ts`：生产不再保留未接线的 `independentPagesMemory`，或把它的句子并进 `formatVerifiedPagesForPrompt`。
  - `chrome-extension/src/background/task/__tests__/manager.test.ts` 与 `agent/backends/__tests__/`：补 SERP 三条打开；双 URL 与有序拒绝已有，不要再铺一套循环。
- 非目标:
  - 不实现 `RunnableParallel` 三条 LLM 链，不实现 `ParallelAgent` / `MergerAgent`。
  - 不在同一 DOM 上并行点两个按钮。
  - 不一次打开超过 `MAX_PARALLEL_TABS`（5）个标签。
  - 不把并行打开做成侧栏新栏目；仍按发生的事列出页卡片。
  - 不恢复 `planner.ts` / `navigator.ts`；不让两个 `TaskSession` 同时 `running`。
