# 第 13 章：人机协同（Human-in-the-Loop）

## 书里的机制

- 人类监督：人看着智能体的表现和输出，用日志或实时界面拦住不良结果（「人类监督涉及监控 AI 智能体性能和输出」）。
- 干预和纠正：智能体出错或含糊时，人可以纠正、补数据或改方向（「人类操作员可以纠正错误、提供缺失数据或指导智能体」）。
- 升级策略：事先约定何时、如何把任务交给人，避免超出能力时硬做（「规定智能体何时以及如何将任务升级给人类操作员」）。
- 决策增强：智能体给分析和建议，人做最终决定（「由人类做出最终决定」）。
- 人机协作：常规操作由智能体做，含糊或高风险处由人接手（「人类和 AI 智能体贡献各自的优势」）。
- 用于学习的人类反馈：收集人的偏好去改模型，书里点到带人类反馈的强化学习（「用于学习的人类反馈」「带有人类反馈的强化学习」）。
- 人在循环外：人先定策略和规则，智能体按规则自己跑即时操作（「人在循环外」「人类专家定义总体策略，然后 AI 处理即时操作」）。
- 代码示例是升级工具：识别需要人审的场景后调用 `escalate_to_human`（「使用 escalate_to_human 转接给人类专家」）。

- 部分做成

## 对持节业务的意义

持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。
这一章改的是「交出去之后人还能不能停、能不能把页拿回来、卡住时能不能补一句」，不是逐步点头。
用户点「接管」时，`takeover` 会关跟随、`revealTab` 把任务页拉到眼前、再 `pause`；侧栏从「进行中」变成「已暂停」，输入框出现「继续」。
登录墙或验证码时，`runObserveActLoop` 收到 `waiting_user`，侧栏变成「需要你处理」并写「先在网页里登录，再点继续或重新发指令。」
提交结果不确定时，`persistAttempt` 把状态写成 `waiting_user` + `commit_outcome_uncertain`，输入框被 `taskLocksComposer` 锁住，用户只能停掉再重新委托，避免重复提交。
这本书里的评分训练和逐步审批，按产品规则都不该做成：交卷看的是页上能核对的那句话，不是星级，也不是每一步等人点头。

## 完成方案

- Goal: `waiting_user` 的每一种 `WaitReason` 都只有一条用户走得通的下一步（登录/验证码后继续、目标不清时补充、证明时确认、不确定提交或模板缺参时只能停止后重开）；不要逐步审批，不要评分训练。
- Hard bar: 委托做到登录墙时，我看见顶栏「需要你处理」、卡片「先在网页里登录，再点继续或重新发指令。」和按钮「告诉持节继续」；我在页上登录后再发「继续」，任务从 `waiting_user` 回到 `running`。不确定提交时，我看见「当前任务只能停止后重新委托」，输入框不可用，没有「继续」也没有「重试」。
- 改哪些现有文件（不要新开第二套 agent 树）:
  - `pages/side-panel/src/components/TaskStatusCard.tsx`：`skill_inputs_required` 的提示不要再说「再跑一次」，与 `waitReasonHint` 已写的「停止后，从「可再运行」重新填写」对齐。
  - `packages/i18n/locales/zh_CN/messages.json`：`chat_task_hint_uncertain` / `chat_task_hint_skill_inputs` 与卡片实句一致，避免 i18n 仍写「继续或重试」。
  - `pages/side-panel/src/SidePanel.tsx`：`onAdjustDirection` 现在传进 `TaskStatusCard` 后又被丢掉（`taskControls = null`）；要么删掉这条死接线，要么不要假装有「调整方向」按钮。改道继续走输入框 `follow_up`。
  - 不要改 `parseControlPolicyDecision` 去恢复模型随意要人确认；证明按钮只留给 `freezeCriterion` 在代码核不过时写下的 `user_confirmed`。
- 非目标: 逐步审批每个 `click_element`；交卷评分 / RLHF；Google ADK 式 `escalate_to_human` 工具；把 `classifyRetry` 的 `'escalate'` 升成人工队列（当前只在 `createLlmControlDriver` 里当「不要再重试」）。
