# 第 1 章：提示词链（Prompt Chaining）

## 书里的机制

- 复杂任务不要塞进一条总提示词，而是拆成一串更小的子步骤，每一步用专门写好的提示词处理。（「将原本令人却步的问题分解为一系列更小、更易管理的子问题，每个子问题通过专门设计的提示词单独处理」）
- 链之所以叫链：上一步的输出必须作为下一步的输入传过去。（「一个提示词的输出会作为输入策略性地传递给链中的下一个提示词」）
- 单条巨型提示词会忽略指令、丢掉上下文、放大早期错误、撑爆窗口、编造内容；顺序拆开后每步只干一件事。（「指令忽略」「上下文偏离」「错误传播」「幻觉」；「通过将复杂任务分解为聚焦的、顺序的工作流」）
- 步骤之间要传机器能解析的结构（JSON / XML），否则下一步会把含糊自然语言读错。（「指定结构化输出格式（如 JSON 或 XML）至关重要」）
- 两步之间可以插入确定性处理：校验字段、调用外部工具、条件重试缺项。（「允许在模型调用之间插入确定性逻辑，从而在工作流中实现中间数据处理、输出验证和条件分支」）
- 每步可以换角色（分析师 / 撰写者），书里的市场报告例子是：总结 → 用摘要找趋势 → 用趋势起草邮件。（「初始提示词作为"市场分析师"」；「使用摘要，识别前三个新兴趋势」）
- 书给的可运行形状是 LangChain LCEL：`extraction_chain` 抽出规格，再把字符串塞进 `prompt_transform` 转 JSON。（「完整的链将提取链的输出传递到转换提示词的 'specifications' 变量中」）
- 上下文工程是本章后半：系统提示词、检索文档、工具输出、对话历史要在生成前拼成操作环境；不是只改用户那一句的措辞。（「系统提示词」「工具输出」「交互历史」；「即使是高级模型，在提供有限或构建不良的操作环境视图时也会表现不佳」）

- 部分做成

## 对持节业务的意义

持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。

```mermaid
sequenceDiagram
  participant User as 侧栏用户那一句
  participant Classify as classifyStartOrFollowUp
  participant Loop as runObserveActLoop
  participant Control as llm.invoke 控制提示词
  participant Extract as extractWithModel
  participant Super as settleProposedDone
  User->>Classify: 分类；不把 JSON 喂给下一句
  Classify->>Loop: 仅当 execute
  Loop->>Control: 同一条 renderControlSystemPrompt
  Control-->>Loop: JSON 动作或 done
  Loop->>Extract: 仅 extract_content 且 DOM 抽空
  Extract-->>Control: JSON 行进 lastActionMemory
  Control->>Super: claimedResult
  Super-->>User: 正在核对 / 还没做完 / 可核对的那一句
```

这一章会改的是「交出去之后，中间那几轮模型调用怎么接」，不是侧栏预印栏目。

现在用户说「抽出表格再写一句」时，任务卡能长出抽取行，但第二句仍可能被同一条控制提示词一次写完或写飘。

失败场景：控制模型在还没抽出 JSON 时就把 `observation` 写成总结，监督若只看当前页标题也可能放行，用户拿到的那句对不上抽出的行。

编号步骤（「1. 打开 2. 记下标题」）今天只变成计划骨架，不会变成两条专用提示词；用户看见阶段名，核对的仍是最后一句。

`decideUserTurn` 是动手前的分类闸，输出 `kind` 不进入 `buildControlUserPrompt`，不算本章的链。

`planner.ts` / `navigator.ts` 只挂在 `createNanoExecutorDriver`；生产默认 `PERSONAL_AGENT_CORE_BACKEND = 'control'`，`createExecutorDriver` 走 `createLlmControlDriver`，旧规划器不算做成。

## 完成方案

- Goal: 当用户句子带编号步骤、或「先抽出再写成一句」时，`createLlmControlDriver` 为每个子步骤换专用 `SystemMessage`/`HumanMessage`，把上一步 JSON 放进下一步，而不是只把 `numberedStepSegments` 写进同一条 `renderControlSystemPrompt`。
- Hard bar: when I do 「1. 抽出当前页商品名和价格 2. 用一句中文说最贵的是哪个」, I see 任务卡先出现「抽取：商品名和价格」，再出现那一句概括；第二步发给模型的 HumanMessage 含第一步 JSON 数组，且第二步系统提示词不是整份 `CONTROL_SYSTEM_PROMPT_BODY` 动作循环。
- 改哪些现有文件（不要新开第二套 agent 树）
  - `chrome-extension/src/background/agent/backends/control-llm.ts`：在 `decide` 里按当前子步骤选提示词；抽取成功后强制下一轮走「只写用户可见句」而不是再选动作。
  - `chrome-extension/src/background/agent/backends/control-policy.ts`：为「从 JSON 写结果」加短系统提示词，不要复制整份控制循环。
  - `chrome-extension/src/background/task/mission-plan.ts`：`numberedStepSegments` 继续只从用户原句拆段，仍不把原文存进计划。
  - `chrome-extension/src/background/agent/actions/extract-content.ts`：已有 JSON 行；链的下一跳读这些行，不必再写一套抽取器。
- 非目标:
  - 不引入 LangChain LCEL，不复活 `Executor`/`PlannerAgent` 当生产默认。
  - 不接 Vertex 提示优化器，不新开第二个 agent 后端。
  - 不把 `decideUserTurn` 的分类 JSON 拼进控制提示词（那是分类，不是链）。
