# 第 12 章：异常处理和恢复（Exception Handling and Recovery）

## 书里的机制
- 智能体必须先认出故障，再决定重试、换路，或受控停下来，而不是整段崩溃。（「检测问题、启动恢复程序，或至少确保受控失败」）
- 事先要想到工具出错、服务不可用，并准备日志、重试、回退、降级、通知。（「错误日志记录、重试机制、回退方案、优雅降级和通知机制」）
- 错误检测看四类信号：工具输出坏掉、API 状态码（404 / 500）、响应过久、回复格式不对或不知所云。（「无效或格式错误的工具输出」「404（未找到）或 500（内部服务器错误）」「异常长响应时间」「偏离预期格式的不连贯和无意义响应」）
- 检出之后要有处理计划：写日志、对瞬时故障重试（可微调参数）、换备用做法、暂时只保留一部分能力、必要时告人。（「日志记录」「重试」「回退」「优雅降级」「通知」）
- 恢复要把系统拉回可继续的状态：撤销刚做的改动、查清原因、改计划或参数、或交给人或上级系统。（「状态回滚」「诊断分析」「自我纠正」「升级」）
- 此模式可与反思连用：第一次异常后分析原因，换提示词再试。（「如果初始尝试失败并引发异常，反思过程可以分析失败原因，并使用改进的方法（如优化提示词）重新尝试」）
- 用例要求：数据库暂时挂了要告诉用户并升级给人；资金不足不要重复下同一笔单；一批文件里坏掉的跳过、其余继续；爬虫遇到 404/503 要暂停或报告那个 URL。（「将查询升级给人类智能体」「避免重复尝试相同的无效交易」「跳过损坏的文件……继续处理其他文件」）
- 书里的 ADK 例子是 `SequentialAgent`：`primary_handler` 调精确工具，失败后 `fallback_handler` 看 `state["primary_location_failed"]` 再调粗粒度工具，最后 `response_agent` 有结果就呈现、没有就道歉。（「如果为 True，从用户的原始查询中提取城市并使用 get_general_area_info 工具」）

```text
书：  检出 → 记日志 / 重试 / 换工具 / 降级 / 告人 → 回滚或改计划或交给人
持节：LoopFailureCategory → classifyRetry 决定是否再走一轮 → applyOutcome(failed|waiting_user)
      侧栏 deriveFailedResult 一句人话；SW 死后 recoverAttempt 把提交标成 uncertain
```

## 结论
- 部分做成
- 完成度：64
- 一句话：生产路径 `createLlmControlDriver` 把 `classifyRetry` 接到 `runObserveActLoop.shouldRetryFailure`，`TaskManager.applyOutcome` 把失败写成 `failed` + `failureCategory`，侧栏 `deriveFailedResult` 给出一句人话；缺的是状态回滚（`chrome-extension/` 搜 `rollback` / `undo` / `revert` 无命中），且 `classifyRetry` 的 `'escalate'` 没有单独升级路径。

## 对持节业务的意义
持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。

```mermaid
sequenceDiagram
  participant User as 侧栏用户那一句
  participant TM as TaskManager.runCurrentRound
  participant Loop as runObserveActLoop
  participant Retry as classifyRetry
  participant Card as deriveFailedResult
  User->>TM: 交出页面上的事
  TM->>Loop: createLlmControlDriver
  Loop->>Retry: 动作报错时问能不能再试
  alt 瞬时错误且未满 maxFailures
    Retry-->>Loop: retry
    Loop->>Loop: failures += 1 再 observe
  else 确定性错误或预算用尽
    Loop-->>TM: failed + failureCategory
    TM-->>Card: status=failed
    Card-->>User: 一句人话 + 再说一次 / 去设置
  else 登录墙或验证码
    Loop-->>TM: waiting_user
    TM-->>User: 先在网页里登录 / 完成验证码
  end
```

这一章改的是「没做成」那一次，不是做成时的回执。
密钥没配时，侧栏应立刻停并指向设置，而不是空转。
点了半天页没变，用户应看到失败句和「再说一次」，而不是无限转圈。
登录墙应停下来等人，而不是把任务标失败。
扩展重启时若提交卡在 `executing`，必须问人、禁止自动再点一次。

## 完成方案
- Goal: 继续只在 `createLlmControlDriver` + `runObserveActLoop` + `TaskManager` 上检出、有限重试、受控失败；把已有 `classifyCreateExecutorError` 接到 `runCurrentRound`；`'escalate'` 要么删掉要么变成 `waiting_user` / 单独 `failureCategory`，不要新开智能体树。
- Hard bar: when I 清空模型密钥再交一句打开页的任务，I see 「模型或密钥还没就绪，任务没开始做。」和「去设置」，且 `failureCategory` 为 `setup_failed`（不是只靠中文碰巧写成同一句）。when I 让循环用尽失败预算，I see 「试了几轮，还是没做成。」和「再说一次」。when I 在登录墙页上交任务，I see 「先在网页里登录，再点继续或重新发指令。」任务为 `waiting_user`。when I 在外部提交执行中杀掉 service worker 再打开侧栏，I see 「提交结果不确定…」，且不会自动再执行那次提交。
- 改哪些现有文件（不要新开第二套 agent 树）：`chrome-extension/src/background/task/manager.ts`（`runCurrentRound` 的 `catch` 改为 `classifyCreateExecutorError`）；`chrome-extension/src/background/agent/retry-policy.ts` 与 `backends/control-llm.ts`（给 `'escalate'` 一条真实分支，或停止假装有第三条路）；`pages/side-panel/src/presentation/failed-result.ts`（若 escalate 要单独句子）。`action-dispatcher.ts` `recoverAttempt` 保持「标 uncertain、不重放」。
- 非目标: 不实现页面点击/表单的状态回滚；不引入 ADK `SequentialAgent` / `fallback_handler`；不把 `planner.ts` / `navigator.ts` / `Executor` 请回默认 `control`；不把 `AnalyticsService` 扩成用户可见诊断页；不为「跳过损坏文件并汇总」另做批处理引擎。
