# 第 4 章：反思（Reflection）

## 书里的机制

- 智能体先交出一份输出，再评估这份输出或当时状态，用评估结果改进下一轮，而不是把初稿直接当终点。（「评估其自身工作、输出或内部状态」）
- 评估可以是另一次模型调用，也可以是规则集；书把这两条都算反思。（「通常通过另一个 LLM 调用或规则集」）
- 更稳的做法是拆成生产者和评审者：两套指令、两次独立调用，避免自己评自己。（「生产者和评审者」；「使用不同系统提示的两次独立LLM调用」）
- 一轮顺序是执行 → 评估/评审 → 按评审优化或改下一步；可以重复，直到满意或碰到停止条件。（「直至获得满意结果或达到停止条件」）
- LangChain 例里评审者按原任务挑错；没有问题就回固定短语，有问题就列批评，再让生产者按批评改同一份代码。（「CODE_IS_PERFECT」；「请使用提供的批评完善代码」）
- ADK 例里 `DraftWriter` 写草稿，`FactChecker` 回 `ACCURATE` / `INACCURATE` 和理由，顺序管线保证先写后评。（「status」；「ACCURATE」；「INACCURATE」）
- 对话历史要带着任务、上一版输出和上一轮批评一起走，反思才是累积的，不是每次从零评。（「对话历史被维护并在每一步传递」）
- 每一轮多一次模型调用，延迟和费用会上去；时间紧的路径不该无上限地转。（「更高的成本和延迟」）

## 结论

- 部分做成
- 完成度：59
- 一句话：生产路径 `createLlmControlDriver` 里的 `settleProposedDone` 会再调一次 `supervisorLlm.invoke`，`applySuperviseVerdict` 拒绝后走 `runObserveActLoop` 的 `judge_retry`；书里「按批评改写同一份输出」没有对应函数，`CODE_IS_PERFECT` / `reflector_prompt` 在 `chrome-extension/src` 与 `pages/side-panel/src` 无命中，且 `factory.ts` 没有把 `Actors.VALIDATOR` 订到侧栏。

第二次看是两层叠在一起，不是二选一：

- 循环内、还没离开执行器：第二次模型调用。函数是 `settleProposedDone`（`control-llm.ts`），体内 `supervisorLlm.invoke` + `parseSuperviseVerdict` + `applySuperviseVerdict`。
- 循环交出 `candidate_complete` 之后：确定性检查。函数是 `TaskManager.verifyArtifactsIndependently` → `verifyCandidateComplete`，以及 `checkCompletion`、`checkInstructionDeliverable`。`verification-engine.ts` 的 `llmJudge` 字段只出现在测试里，生产调用没传。

## 对持节业务的意义

持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。

用户说「打开第一条视频」或「概括这个页面」并点委托后，工人一旦写 `done`，`settleProposedDone` 会再看当前页再决定能不能停。

这一次第二次模型调用拦的是「页面对不上还说做完」。它不改写摘要文笔，也不评审阶段标题。

核对失败时，用户在 `pages/side-panel/src/SidePanel.tsx` 的任务卡上多看到几步，或最后看到「没有写出可检查的结果。请开新任务再发一次。」

核对成功时，侧栏出现那句可核对结果（或「页面结果已核对」），对应 `persistVerifiedReceipt` 之后的 `completionChatDelivery`。

用户看不见「还没做完：仍在列表页」这类评审句：事件没有订到侧栏。失败时也看不到该重开任务是因为监督拒绝，还是因为 `checkCompletion` 没过。

## 完成方案

- Goal: 生产 control 路径上，第二次模型调用的短句出现在侧栏时间流里；书面结果被确定性检查挡下时，用已有 `addFollowUp` 再要一句可核对的话，不新开第二套 agent。
- Hard bar: when I 委托「打开第一条视频」而当前仍是搜索列表页, I see 侧栏出现「正在核对页面上的结果」，随后一条「还没做完：…」，任务继续点进视频而不是直接完成。when I 委托「概括这个页面」而第一句是「好的，我来阅读…」, I see 同一任务里出现第二句可核对概括，而不是立刻 `chat_task_fail_no_deliverable`。
- 改哪些现有文件（不要新开第二套 agent 树）
  - `chrome-extension/src/background/agent/factory.ts`：`createExecutorDriver` 把已有 `onEvent` 传进 `createLlmControlDriver`（今天只传给 nano）。
  - `chrome-extension/src/background/agent/backends/control-llm.ts`：在自建的 `EventManager` 上订阅 `EventType.EXECUTION` 并转给 `onEvent`，让 `settleProposedDone` 的 `Actors.VALIDATOR` 事件到达 `background/index.ts` 已有的 `sidePanelPorts.broadcast`。
  - `pages/side-panel/src/presentation/humanize-message.ts`：确认 `还没做完：` / `正在核对页面上的结果` 走 `append_assistant`，不要被 `isProcessNoiseContent` 吃掉（当前这两句不在噪声名单里）。
  - 不要为了书里的改稿循环新写一套 LangGraph。书面结果继续用 `checkInstructionDeliverable` + `driver.addFollowUp`；若要「按批评改一句」，把 `applySuperviseVerdict` 拒绝理由原样拼进已有 follow-up 字符串即可。
- 非目标:
  - 不复活 `planner.ts` / `navigator.ts` 当评审者。
  - 不给每一次点击都加评审调用。
  - 不实现 `CODE_IS_PERFECT` 式代码改稿，不把 `llmJudge` 接进 `verifyArtifactsIndependently`（确定性失败仍不可被模型救活；语义分未接线是刻意缺口，除非有用户可见的摘要质量场景）。
  - 不新开第二个 extension 或第二套循环。
