# 第 11 章：目标设定与监控（Goal Setting and Monitoring）

## 书里的机制

- 先写下具体目标，再给一套对照目标看进度、判断是否做成的手段（「为智能体设定具体的工作目标，并为其配备跟踪进度和确定这些目标是否已实现的手段」）。
- 目标要写成目标状态，并知道从哪出发（「决定想去哪里（目标状态），弄清楚从哪里出发（初始状态）」）。
- 目标要用 SMART：具体、可衡量、可实现、相关、有时限（「目标应该是具体的、可衡量的、可实现的、相关的和有时限的（SMART）」）。
- 监控要看行动、页面/环境、工具输出，并预先写清成功标准（「清楚地定义指标和成功标准」「监控涉及观察智能体的行动、环境状态和工具输出」）。
- 书里的示例循环是：生成 → 按目标清单自评 → LLM 只答 True/False → 未达成就改再试，最多 5 轮（「仅用一个词回答：True 或 False」「我使用最多 5 次迭代」）。
- 未达成时要改计划或交给人（「来自监控的反馈循环允许智能体适应、修订计划或升级问题」）。
- 同一模型既写又判容易自欺；更稳的是把审查员拆开（「当同一个 LLM 既负责编写代码又负责判断其质量时」「分离这些关注点」）。
- 没有步数上限，监控会让进程一直跑（「造成了进程可能永远运行的潜在风险」）。

## 结论

- 部分做成
- 完成度：70
- 一句话：`TaskManager` 主路径会 `freezeCriteria`、`checkCompletion`、`persistVerifiedReceipt`，页面对上才停；但 `deriveMissionGoal` 永远写成「执行任务」，`TaskProgressOverview` 不画阶段验收条，仓库里没有把用户那一句改成 SMART 目标的函数。

## 对持节业务的意义

持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。

用户点发送之后，真正决定「能不能停」的是 `checkCompletion` 和 `persistVerifiedReceipt`，不是模型那句 done。
打开站点、播视频、关标签这类事，`extractImplicitCompletionCriteria` 会冻住 `url` / `media_state` / `tab_state`，动作之后 `tryVerifyAfterSuccessfulAct` 会再探一次页面。
读页面写摘要这类事常常冻不住条件，就会走「有一句像样的结果就交」；空合同 `deriveInstructionDeliverableContract` 不再按表格/条数卡死。
侧栏不预印目标栏，也不画阶段清单；用户要靠原句、打开的页、最后那句结果来对。
失败场景：模型说做完了但 `/watch` 没到，没有 `completion-receipt`，会再试一轮或看到「试了几轮，还是没做成。」
多件事（播放 + 复制评论）时，`assessGoalCoverage` 交卷后画出「只完成了部分目标」，让用户补那句没交出来的话。

## 完成方案

- Goal: 用户那一句对应的已冻结条件，在侧栏能被看见；只有这些条件通过后才出现 `completion-receipt`。
- Hard bar: 当我说「打开 YouTube 并点击第一个视频」，侧栏沙卡仍是这句话（不是「执行任务」）；落地 `youtube.com/watch` 且 `checkCompletion` 通过后出现回执和「页面地址已符合目标」；模型只输出 done、地址仍是首页时，没有回执。
- 改哪些现有文件（不要新开第二套 agent 树）
  - `pages/side-panel/src/components/TaskProgressOverview.tsx`：把 `deriveTaskProgressView` 已算好的 `milestones[].gates`（「验收条件」`current/target`）画出来；不要恢复 `MissionPlanList`。
  - `chrome-extension/src/background/task/manager.ts`：无条件路径失败时，让 `deriveFailedResult` 能读到比 `no_completion_criteria` 更具体的一句（缺的是回执还是正文）。
- 非目标:
  - 不要把用户原句写进 `MissionPlan.goal`（隐私：原句、邮箱、密钥不得进计划）。
  - 不要实现书里的 `goals_met` True/False 作为停的条件。
  - 不要恢复从动词猜任务类型的 `deriveInstructionDeliverableContract`（Decision 005）。
  - 不要为审查员再开一套 agent 树；审查继续走 `settleProposedDone` + `checkCompletion`。
