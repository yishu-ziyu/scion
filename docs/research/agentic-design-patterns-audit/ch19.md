# 第 19 章：评估和监控（Evaluation and Monitoring）

## 书里的机制
- 评估是部署后对效能、效率和合规的持续外部测量，不只是写单元测试（「持续的（通常是外部的）测量」）。
- 要先定义指标：准确性、延迟、资源消耗（含 LLM token），并落到持久存储而不是只打印（「延迟监控」「跟踪 LLM 交互的 Token 使用量」）。
- 生产里要做性能跟踪、版本对比（A/B）、合规审计、漂移检测、行为异常检测（「实时系统中的性能跟踪」「A/B 测试」「漂移检测」）。
- 简单字符串精确匹配不够；真实评估要用语义指标或 LLM-as-a-Judge（「evaluate_response_accuracy」「LLM-as-a-Judge」）。
- 必须评轨迹：把实际工具步骤和理想序列比（精确匹配 / 按序 / 任意顺序 / 精确度 / 召回率）（「智能体轨迹」）。
- 评估物分测试文件（单会话单元）和评估集文件（多会话集成）；入口可以是 Web UI、pytest、CLI（「Google 的 ADK」「adk eval」）。
- 高风险任务要用正式合约：可验证交付物、协商、自我验证、子合约拆分（「从智能体到高级承包商」「正式化合约」）。

## 结论
- 部分做成
- 完成度：50
- 一句话：`eval-matrix.mjs` / `taskSpecificVerificationPass` 能离线打 `verified_pass` 与 TSR，主路径 `persistVerifiedReceipt` 与 `settleProposedDone` 能拦住假完成；但 `createLlmControlDriver` 不调用 `AnalyticsService.trackTaskStart`，`control-llm.ts` 的 `llm.invoke` 也不记录 token，仓库里没有 `concept drift` / `anomaly` 检测函数。

## 对持节业务的意义
持节业务 = 用户把页面上的事交出去，侧栏按发生的事往下长，交出能核对的结果。
这一章对应的是：用户点发送之后，系统凭什么把侧栏写成「已完成」，以及维护者怎么知道下一版变差了。
用户操作：交一句「打开维基百科并摘标题」→ `TaskManager.dispatch` → `createLlmControlDriver` / `runObserveActLoop`；工作者说做完时 `settleProposedDone` 再看一页；`persistVerifiedReceipt` 写回执后，`TaskStatusCard` 才出现可复制成果。
侧栏：`pages/side-panel/src/components/TaskStatusCard.tsx` 的回执块、`WorkStream` 的发生记录；选项页的 Analytics 开关不改变这条完成路径。
失败：核对不过时用户看到失败句或「还没做完」；假完成（UI 写完成但页面不对）只在 `eval-public-task.mjs` 记 `false_complete`，用户侧栏没有单独的「这次是假完成」标记。
漂移和 token 费用：用户和选项页都看不到，维护者也没有生产曲线，只能靠下次手跑 `pnpm eval:matrix`。

## 完成方案
- Goal: 控制路径（`createLlmControlDriver` + `TaskManager`）在任务完成/失败时写下与评估行同口径的耗时和结果；token 若 API 返回 usage 则记在 `TraceSpan.data`。不新开第二套 agent。
- Hard bar: when I 用控制路径做完一件有回执的事且选项里打开了 Analytics，I see PostHog 事件 `task_completed` 带 `duration_ms`，且 `trackTaskStart` 的调用栈经过 `manager.ts` 而不是 `executor.ts`。when I 跑 `pnpm eval:gate` 对比两份已签名 CSV，I see TSR / Pass^3 回归会失败。
- 改哪些现有文件（不要新开第二套 agent 树）
  - `chrome-extension/src/background/task/manager.ts`：在 `persistVerifiedReceipt` 成功、以及 round 标 `failed` / `cancelled` 处调用 `analytics.trackTaskComplete` / `trackTaskFailed` / `trackTaskCancelled`。
  - `chrome-extension/src/background/services/analytics.ts`：`trackTaskComplete` 必须有调用方；可加 `failure_category`（已有 `round.failureCategory`），不要新平台。
  - `chrome-extension/src/background/agent/backends/control-llm.ts`：`llm.invoke` / `supervisorLlm.invoke` 后若响应带 `usage`，写入已有 `traceStore.finishSpan` 的 `data`（`input_tokens` / `output_tokens`）。
  - 不要把 `llmJudge` 接到 `verifyArtifactsIndependently`，除非先写确定性失败仍不可被 judge 救回的回归（`verification-engine.test.ts` 已有形状）。
  - 评估仍用 `taskSpecificVerificationPass`；不要为了本章去加 ADK Web 或在线 A/B。
- 非目标: 概念漂移检测器、Datadog/Prometheus、多智能体评测、学习曲线 UI、书里的承包商协商协议、把 `planner.ts` / `navigator.ts` 重新接回生产。
